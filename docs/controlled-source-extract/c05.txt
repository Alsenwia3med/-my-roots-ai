ROOTS-AI™ C-05 UI/UX Screen Implementation
Specification v1.0.1 — CONTROLLED CORRECTION
Document ID: ROOTS-C05-UIUX-001 | Controlled correction to v1.0.0
This correction sheet is integral to the attached v1.0.0 release and supersedes only the clauses identified below. All unaffected screen
inventory, routes, functional states, role visibility, responsive acceptance, accessibility, security and evidence requirements remain binding.
1. Authority and conflict rules
Supersedes Section 1 where visual authority or legacy versions conflict. Master Requirements control scope, security, data behavior,
delivery and acceptance. C-01 v1.0.1 controls question wording/types/options/validation; C-02 v1.0.1 controls deterministic
scoring/classifications/drivers; C-03 v1.0.1 controls the 19-section report content/data contract and governed report states; C-04 v1.0.1
controls website/legal/consent/system/error copy. C-05 controls screen inventory, composition, navigation, functional states,
responsiveness and role visibility. Final aesthetics, component appearance, final tokens and visual hierarchy are governed by the
ROOTS-AI Visual Direction and, after written ROOTS-AI approval, the PUB-01 Golden Screen/design system. Functional/content
authority and visual authority apply together; neither may change the other's controlled requirements.
2. Existing SVG / wireframe boundary
Any existing SVG or prior screen reference is authoritative only for approved content, required elements, structure, flow and functional
intent where applicable. It is FUNCTIONAL AND CONTENT WIREFRAME — NOT A FINAL VISUAL DESIGN. No filename containing
“FINAL” or prior visual mockup overrides the Visual Direction or a written-approved Golden Screen.
3. Section 5 — responsive grid and visual tokens
Breakpoints remain binding: 360–767, 768–1023, 1024–1439 and ≥1440 px, with required evidence at 360/768/1024/1440. Accessibility,
minimum readable legal text, visible focus, touch-target and reflow requirements remain binding. The listed Inter/Arial choice, fixed heading
sizes, 8-px spacing scale, navy/soft-navy/warm-white/charcoal/muted/focus/error hex values, grid styling and other aesthetic token values
in v1.0.0 are legacy/implementation references, not final visual tokens. Final visual tokens are established through the approved
Golden Screen/design system. Styling must never weaken accessibility, content meaning, state semantics or functional acceptance.
4. Assessment validation alignment
All assessment screens shall implement C-01 v1.0.1 exactly. A required multi-select response must contain one or more approved option
IDs; an empty array is invalid. NONE/N/A is exclusive where provided and cannot be combined with other options. Q73 does not permit
N/A. No UI behavior may weaken canonical validation.
5. Report driver and null-state alignment
All report screens shall render the exact C-02/C-03 v1.0.1 deterministic outputs. Driver rendering supports zero to three output entries; a
co-primary pair is one output entry. Do not invent, duplicate or back-fill an ineligible/null driver or protective factor for layout symmetry.
Reduced and Not Available states defined by C-03 must be supported. The domain ID BS remains Biological Safety Signals™ and must
not be used as the Biological State identifier.
6. Golden Screen gate before downstream visual finalization
PUB-01 is the mandatory Golden Screen. The Implementation Partner shall first provide the required direction work and then the selected
PUB-01 at the controlled responsive sizes in an editable Figma file in a ROOTS-owned workspace, including
components/tokens/states/responsive notes and editable assets. No remaining screen may be visually finalized in bulk before written
ROOTS-AI approval of PUB-01. After approval, downstream screens shall inherit that approved visual system while preserving this C-05
functional specification.
7. UI-019
Supersedes UI-019. ROOTS provides written approval of the PUB-01 Golden Screen before downstream visual finalization. During UAT,
ROOTS additionally approves the complete screen inventory, controlled-breakpoint responsive evidence, accessibility evidence and
visual-regression baseline/results against the approved Golden Screen/design system.
8. Section 15 — required handover artifacts
Supersedes the statement “No separate Figma file is required...” Editable Figma is mandatory for the Golden Screen and resulting
approved visual system and must reside in or be transferred to a ROOTS-owned workspace. The existing component catalog, route
inventory, 360/768/1024/1440 screenshots, visual-regression evidence, accessibility evidence, browser/device report, licenses, editable
assets, content mapping and defect disposition remain required. Figma does not replace or weaken executable code, evidence, C-05
functionality, or other controlled handover artifacts.
9. Integrity / no scope expansion
These corrections do not change the 73-question / 13-module assessment, 19-section report, route inventory, role/security restrictions,
autosave/resume requirements, offline/error states, WCAG 2.2 AA target, browser compatibility, or the fixed commercial scope/schedule.
They correct reference authority and implementation sequencing so that functional wireframes cannot be mistaken for final visual design.
Precedence: where the attached v1.0.0 pages conflict with this sheet on the matters above, v1.0.1 controls.

6. Component Contract
Component Required anatomy States and rules
Button Primary, secondary, tertiary/text, destructive Default, hover, focus, active, disabled, loading; one primary
per action region
Text input Label above; hint below; required marker in text Default, focus, filled, disabled, error, success; error tied with
aria-describedby
Select/radio/checkbox Visible label and full-row click target Keyboard selection; never rely on placeholder as label
Question card Question ID hidden from participant; prompt,
help, control, validation
One question at a time on mobile; grouped only where
explicitly compatible
Progress Module n of 13 plus percentage Text equivalent; no score implication;
completed/current/future states
Alert Info, success, warning, error Icon + title + text; announced appropriately; persistent for
blocking error
Modal Title, purpose, body, primary/secondary actions Focus trap; Escape only when safe; return focus to trigger
Toast Non-blocking save/success confirmation Auto-dismiss ≥5 s with pause; never sole display of a
blocking failure
Card Heading, body, optional metadata/action Whole-card link only when one destination; visible focus
Tabs Maximum 5 visible; otherwise use select/drawer URL/state preserved; arrow-key navigation
Table Caption, headers, sorting/filter controls Horizontal scroll on mobile; stacked cards only if
relationships remain clear
Score bar Label, numeric value, classification, bar Text and number always present; color not sole meaning
Skeleton Structure-matched loading placeholder No false data; replace with retryable error on timeout
Empty state Reason, safe explanation, permitted next action No fabricated data; role-aware CTA
